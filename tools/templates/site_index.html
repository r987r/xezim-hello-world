What is implemented?

Actual chip boot

PicoRV32 coordinates SERV through init, run and check mailboxes. CPU0 reads ROM/flash, copies firmware into uninitialized SRAM over the bus and releases CPU1 through MMIO. Both execute from SRAM.

Memory and bus models

Why does DMA appear? Why SLVERR?

DMA varies by verification scope

The default cold-boot scope disables its optional engines and may use a BFM at a reserved DMA port. Other full-chip variants connect real PULP iDMA engines through the NoCs. Check the specific run's manifest and source SHA before treating DMA activity as verified.

Explicit error-path tests

Normal CPU boot expects successful responses. The NoC BFM deliberately requests 24 write/read SLVERR pairs. The chip BFM deliberately accesses beyond both 64-KiB memory models: four SLVERR transactions. New reports mark each exact expected request; undeclared initiator errors fail capture validation.

Older reports retain their original unannotated data. Downstream observations of an error are not additional initiator failures. Neither captured AXI traffic nor compile-only evidence proves physical memory controllers or DMA integration.
